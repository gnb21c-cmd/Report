## 2. 지금 상태 (확인한 것)

| 묶음 | 저장소 | 도는 방식 | 자료 |
|---|---|---|---|
| A · B · D · D-1 + 자동 수집 | `Report` (공개) | 화면은 Firebase Hosting, 계산은 각 화면 안. 자동 수집은 **GitHub 예약 작업(cron)** → POS 메인 PC 의 실행기 `nice-pos` 에서 OKPOS 점주 웹 · 나이스 · 네이버를 화면으로 읽음 | Firebase Firestore (무료 판) |

## 3. 통합 구조 (제안)

```
 [카페 POS 메인]                         [키즈 입구 POS]
  ├ GitHub 실행기 nice-pos (지금 그대로)    ├ C 아스타나키즈 통합데스크
  │   아침 09:10~10:12 어제 확정 수집        │   ├ 데이터 디스크(설치 폴더 밖) 보관 ← 다시 깔아도 남음
  └ POS 상주 전송기 (새로) ── 10분마다 ──┐  │   ├ 고객 대장 엑셀(비밀번호) · 블랙컨슈머 ← 이 PC 안에만
                                       │  │   └ 오늘 키즈 숫자 ── 10분마다 ──┐
                                       ▼  ▼                               ▼
                         Firebase Firestore (무료 판, 매장 열쇠 아래 통로들)
     reports/{날짜} 확정 ← A · 자동 수집        live/{날짜} 마감 전 ← 전송기 · C
     orders/{날짜} ← D        inv/* · invIn · invCount ← E-1        alerts ← E
                                       │
     B 폰: 어제까지 = 확정 / 오늘 = "마감 전 영업정보" (D 생산량 포함)
     D-1: 오늘 생산 + 내일 준비 (지금 그대로)
     E (매일 아침 GitHub): 어제 판매 × 레시피, 베이커리는 D 생산량 × 레시피 → 재고 줄임 → 안전재고 아래면 F 푸시 (FCM, 무료)
```

**통로 원칙**: 시스템끼리 서로의 코드를 부르지 않고 Firestore 문서(또는 그 PC 안 파일)로만 주고받는다. 통로마다 쓰는 쪽 · 읽는 쪽 · 공개 범위를 `ports.ts` 한 표에 적고 시험으로 검사한다. 무료 판에는 Cloud Functions 가 없으므로, 계산은 화면 · GitHub 예약 작업 · POS 상주 전송기에서 한다.

## 6. 정할 것 (사용자 결정)

### ① 구동 방식 — 마감 전 숫자를 어떻게 올릴지
| 안 | 장점 | 단점 |
|---|---|---|
| **가. 아침 확정은 지금 GitHub 예약 작업 그대로 + 오늘 숫자만 POS 상주 전송기 (추천)** | 검증 끝난 아침 수집을 건드리지 않음. 10분 간격이 정확, GitHub 이 늦어도 상관없음 | POS 메인 · 키즈 PC 에 작은 프로그램 하나씩 설치(작업 스케줄러). 설치 위치는 그대로 |
| 나. 전부 GitHub 예약 작업 (10분마다) | 새 설치 없음 | 15~30분씩 늦는 날이 많고 실행 기록이 하루 70개 넘게 쌓임 |
| 다. 전부 상주 전송기로 옮김 | 한 방식 | 지금 잘 도는 아침 수집 로직을 바꿔야 함 (삭제 · 변경이라 권하지 않음) |

### ② 재고(E · E-1 · F)를 어디에 만들지
| 안 | 장점 | 단점 |
|---|---|---|
| **가. Report(Firebase 무료)로 — astana 의 재고 계산 코드를 옮겨 씀 (추천)** | 서버 비용 0, B 상품명 · D 생산량과 같은 곳이라 통로가 짧음. astana 쪽은 지우지 않음 | 화면을 새로 옮겨 만들어야 함. Firestore 문서 크기(1MB) 때문에 원재료 · 레시피를 몇 문서로 나눠 둠 |
| 나. astana 서버(PostgreSQL)에서 계속 | 이미 만든 화면 · DB 그대로 | 운영 서버(유료 클라우드)가 필요하고, Firebase 와 서버 사이 다리를 따로 만들어야 함 (통신 지점이 늘어남) |

### ③ 개인정보 원칙 고치기
지금 원칙: "카드번호 · 전화번호 등 개인정보는 다루지 않는다". 고칠 안: "**고객 대장 · 블랙컨슈머만 키즈 POS(C) 안에서, 책임자 비밀번호로 잠근 파일로 다룬다. 클라우드 · 저장소 · 실행 기록 · B 에는 숫자만**". 네이버 수집기의 '이름 · 전화 뒷자리는 메모리에서만' 원칙은 그대로.

### ④ 블랙컨슈머 예약 자동 취소 기준
| 안 | 장점 | 단점 |
|---|---|---|
| **가. 이름 + 전화번호 전체가 같을 때만 자동 취소, 뒷자리만 같으면 근무자 화면에 '확인 필요'로 (추천)** | 다른 손님을 잘못 취소하지 않음 | 네이버 목록에서 전화 전체가 안 보이면 예약 상세를 한 번 더 열어야 함 |
| 나. 이름 + 뒷자리 4자리로 자동 취소 | 빠름 | 동명이인 · 같은 뒷자리면 잘못 취소 → 민원 위험 |

설정 기본값은 **꺼짐**. 켤 때마다 기록을 남김.

## 6-1. 정한 것 (2026-10-07)
- ① 가: 아침 확정은 지금 GitHub 예약 작업 그대로 + 오늘 숫자만 POS 상주 전송기
- ② 가: 재고(E · E-1 · F)는 Firebase(Report)로 — astana 의 재고 계산을 옮겨 씀, astana 는 지우지 않음
- ③ 고객 대장 · 블랙컨슈머만 키즈 POS(C) 안에서 책임자 비밀번호로 잠근 파일로. 클라우드 · 저장소 · 실행 기록 · B 에는 숫자만 — **수치 · 통계 · 보여지기에 오류가 없어야 함**
  → 오늘 카페 · 키즈 숫자는 확정 보고와 **같은 계산**(`buildStorePart`)으로 만들고, B 는 받은 조각을 `live.ts` 로 검사해 틀리면 보여 주지 않고 '확인 필요'로. 전화번호처럼 생긴 글 · 정해지지 않은 칸이 섞이면 막음
- ④ 가: 이름 + 전화번호 전체가 같을 때만 자동 취소, 뒷자리만 같으면 '확인 필요'. 설정 기본값 꺼짐
