# 매장 POS 일일 보고 시스템 — 검토 · 가능성 · 계획 (2026-10-02, 같은 날 결정 반영)

## 1. 하려는 것 (요청 정리)

지금: 매일 아침 사람이 POS 를 보고 집계해 그룹웨어로 보고합니다.
바꾸려는 것: 회사 안 몇 사람이 **전날까지의 매출·분석을 폰에서 언제든** 보도록 자동으로 보고되게 합니다.

| 번호 | 프로그램             | 하는 일                                                                                          |
| ---- | -------------------- | ------------------------------------------------------------------------------------------------ |
| ①    | POS 자료 추출        | 카페 메인 POS · 키즈 POS 에 설치. 정해진 시간에 POS DB 에서 자료를 꺼냄 (키즈는 근무자가 송부 버튼도) |
| ②    | 집계 · 분석 · 보고   | ①의 자료를 받아 일일·월 누계·비교·순위로 정리                                                   |
| ③    | 폰 보기              | ②를 필요한 사람 폰에 설치. 전날까지의 보고를 언제든 확인                                         |

조건
- 외부 공개 아님. 회사 안 몇 명만.
- 우리가 운영하는 서버는 두지 않음.
- POS 는 10시 ~ 22시 켜져 있음. 키즈 POS 는 손님이 없으면 21시 반쯤 끔 → 끄기 전에 근무자가 **송부 버튼**.
- 네이버 예약 입장은 키즈 POS 에 **0원 상품코드**로 찍힘 (입장권 발행용). 근무자가 한두 장 더 찍고 완료 처리해 네이버 판매 수와 안 맞을 수 있음 — 매출 회계에는 문제 없어 그대로 둠.

아스타나 앱(`gnb21c-cmd/astana`)과는 **별도 운용**합니다. 아스타나에서 만든 POS 읽기 코드·점검 결과·보고 계산 방식만 가져다 씁니다.

## 3. 가능성 검토

### 3-1. ① POS 자료 꺼내기 — 가능. 방법은 3가지, 계정 없이 되는 것부터

| 방법                                     | 계정 필요 | 실시간 | 상태                                                                                       |
| ---------------------------------------- | --------- | ------ | ------------------------------------------------------------------------------------------ |
| A. OK포스 보고서 엑셀 읽기               | 아니오    | 아니오 | **바로 가능**. "상품별 (일자별)" 엑셀 읽는 코드가 이미 있음 (아스타나 `xls_report.py`)      |
| B. OK포스 DB 직접 읽기 (Firebird, 읽기만) | 예        | 거의   | 코드 있음 (`firebird.py`, 읽기 전용 트랜잭션). **OK포스에서 읽기 전용 계정**을 받으면 바로  |
| C. POS 가 결제 때 남기는 파일 읽기       | 아니오    | 거의   | 결제 때 `CFG\XML\SL010.xml`·`SL011.xml`·OK포스 기록이 바뀌는 것 확인. 안에 무엇이 있는지 점검 필요 |

- **시작은 A** 로 합니다. 계정을 기다리지 않고 바로 쓸 수 있습니다. "실시간은 아니어도 확보 가능"한 길이 이것입니다.
  - 마감 때 근무자가 OK포스 백오피스에서 "상품별 (일자별)" 을 정해진 폴더에 저장 → ①이 폴더를 지켜보다 바로 읽어 보냄.
  - 손이 한 번 가는 대신, 조회줄수(5000)·한 달씩 등 잘림 검사가 이미 들어 있어 잘린 파일은 보내지 않습니다.
  - OK포스에 "보고서 자동 저장" 기능이 있는지도 함께 묻습니다. 있으면 근무자 손도 필요 없어집니다.
- **B 가 되면 바꿉니다.** 계정을 받으면 설정 한 줄만 바꾸면 되고, 근무자 조작 없이 정해진 시간·송부 버튼으로 바로 꺼냅니다.
- **C 는 점검 도구로 확인**합니다. XML 에 하루 판매가 들어 있으면 계정 없이도 자동이 됩니다 (OK포스 파일은 읽기만).

### 3-2. "서버 없이" — 그대로는 안 되고, **우리가 운영하지 않는 저장소 한 곳**은 필요

이유
1. **카페와 키즈가 다른 망**(192.168.0.x / 172.30.1.x)이라 두 PC 가 서로 직접 주고받을 수 없습니다.
2. 폰은 매장 밖(집·출장)에서도 봐야 하는데, POS PC 는 밤에 꺼집니다. 꺼진 PC 에서는 폰이 받아 올 곳이 없습니다.
3. 매장 PC 를 인터넷에 직접 열면(포트 열기) 결제 PC 가 위험해집니다.

그래서 **우리가 서버를 만들고 관리하지 않는, 이미 있는 클라우드 보관함**을 우편함처럼 씁니다.

```
[카페 메인 POS] ─① 추출─┐
                         ├─(HTTPS, 그날 묶음)──▶ [클라우드 보관함] ──▶ [폰 앱 ③] (받아서 폰에 저장)
[키즈 POS]     ─① 추출─┘         (우편함)            ▲
   └ 송부 버튼                                      └ ② 집계는 폰 앱 안에서 (서버 계산 없음)
```

- 보관함 후보 (월 비용 0원 수준, 몇 명이 쓰는 양):
  - **Firebase (Firestore + 로그인)** — 추천. 폰 앱 연동이 쉽고, 읽을 사람을 계정으로 막기 쉬움. 무료 사용량 안.
  - Google 드라이브 / 스프레드시트 — 사람이 표로도 볼 수 있음. 폰 앱 연동은 조금 번거로움.
  - Supabase — Firebase 와 비슷.
- 보관함에 올리는 것: **날짜·상품명·분류·수량·금액뿐**. 카드번호·전화번호는 ①이 버립니다 (아스타나 `normalize.py` 규칙 그대로).
- ② 집계는 **폰 앱 안에서** 합니다. 보관함은 그날 묶음만 들고 있으면 되어 서버 프로그램이 필요 없습니다.

> 정말 클라우드도 쓰지 않으려면: 카페 메인 PC 를 집계 PC 로 두고, 키즈 PC 는 송부 버튼으로 카페 메인에 보내고(망이 달라 결국 인터넷 경유 필요),
> 폰은 매장 와이파이에 있을 때만 받아 오는 방식이 됩니다. 매장 밖에서 못 보고 망 문제가 커서 **권하지 않습니다.**

### 3-3. ② 집계·분석 — 가능. 아스타나 대표자 보고 계산을 옮겨 씀

아스타나 `report.ts` 중 **POS 자료만으로 되는 것**을 가져옵니다 (앱 주문·예약·인건비는 이 시스템에 없음).

| 보고                   | 내용                                                                                         |
| ---------------------- | -------------------------------------------------------------------------------------------- |
| 전일 요약              | 카페 · 키즈 · 합계 실매출, 결제(총매출·할인), 전주 같은 요일 대비                            |
| 팀별                   | 바리스타 · 베이커리 · 키친 · 키즈 · 기타 (POS 대분류·상품명으로 나눔, 모르면 '기타'로 따로) |
| 당월 누계 · 예상 월매출 | 1일 ~ 전일 누계, 남은 날 요일별 평균으로 예상                                                |
| 작년 비교              | 작년 같은 달 같은 날까지 (지난 자료 2025-09 ~ 를 처음에 한 번 넣음)                          |
| 상품 순위              | 전일·이달 많이 팔린 / 안 팔린 상품 (상품명 기준, VAN 전후 이어서)                             |
| 키즈 입장              | 현장 결제 입장권 수·금액, **네이버 입장(0원 코드) 장수**, 추가 인원                           |

- 네이버 입장 수는 "POS 발행 장수"로 표시하고 "근무자 추가 발행이 섞일 수 있음"을 작게 적습니다. 매출 금액은 0원이라 합계에 영향 없음.
- 반품·취소는 음수 그대로 더합니다. 같은 날을 다시 받으면 그날을 **통째로 바꿔** 두 번 더해지지 않게 합니다 (아스타나 `replaceDays` 규칙).

### 3-4. ③ 폰 보기 — 가능

- 안드로이드 · 아이폰 모두: **설치형 웹앱(PWA)** 로 시작 — 홈 화면에 아이콘, 앱처럼 열림, 앱스토어 심사 없음, 받은 자료는 폰에 저장되어 인터넷 없어도 지난 보고를 봄.
- 볼 사람만 로그인 (관리자가 허락한 구글 계정·전화번호). 링크가 새도 못 봄.
- 매일 아침 "어제 보고 도착" 알림 (선택).
- 필요하면 나중에 안드로이드 설치 파일(apk)로도 묶음.

| 3    | 누계 2 × 2                             | 당월 누계 · 올해 누계 / 작년 같은 달 누계 · 작년 같은 기간 누계 (예상 월매출은 뺌)                          | 당월 · 올해 누계 상세        |
| 4    | 방문 · 소비 (추정)                     | 추정 방문자 = 음료·맥주 잔 수 × 0.96 · 1인 평균 소비 = 총 매출 ÷ 추정 방문자                                 | 각 상세                      |
| 5    | 키즈 입장권                            | 네이버 예약(0원 코드 수, **고칠 수 있음**) · 현장 구매(입장료 결제 수)                                       | 각 상세 (고치기 칸)          |

상세 화면 = 그날 값 + 추세 선 그래프(14일 · 30일 · 90일 · 12개월, 점을 누르면 그 날짜로) + **분석 설명**(지난주 같은 요일 · 최근 4주 같은 요일 평균 · 최근 7일 흐름 · 30일 최고/최저 · 주말 대 평일 · 이달 누계 비교) + 항목별 속(상품, 입장권 계산, 잔 수).

계산 규칙 (`packages/core/src/rules.ts`, `metrics.ts`)
- 키즈 입장권 (2026-10-02 사장님 기준, 실제 자료 10/1 · 9/27 로 확인)
  - **입장 발행** = 0원 입장권 수량 합 ('[평일] 무제한 이용' · '야간자유입장권' · 주말 시간대별 '○시 퇴장 [○시 입장]') — 네이버·현장 손님 모두에게 나감
  - **현장 구매** = 돈을 받은 입장권 수량 ('[평일]/[휴일] 1시간 50분 입장권', 환불은 -1)
  - **네이버 예약** = 입장 발행 − 현장 구매 (10/1: 20 − 4 = 16). 관리자가 고치면 그 값 (모든 폰에 같이 보임, 고친 사람·시각 남김)
  - **이벤트 무료입장** = 0원 쿠폰 입장 팀 수 ('[평일] 한가위 무제한 쿠폰', 분류 서비스.쿠폰 — 11/30 까지, 앞으로 다른 이벤트도 같은 칸)
- 키즈 입장료 = (네이버 예약 + 현장 구매) × 단가. 단가: 평일 12,000원, 평일 외(토·일·공휴일·대체공휴일) 14,000원. 이벤트 무료입장은 0원
- 기타 = 카페 POS 기타 + 키즈 POS 의 입장권 외 매출 (추가 인원 · 간식 등)
- 총 매출 = 다섯 상자의 합 (네이버 입장권 매출이 들어가므로 POS 실매출 합보다 큼)
- 날씨: 기상청 관측(지난 날)·예보(오늘)를 A 가 받아 날짜별로 쌓음 → 지난 날을 골라도 그날 날씨가 그대로 보임. 상세 분석에 그날 날씨 한 줄과 "최근 90일 비·눈 온 날 평균 vs 맑은·흐린 날 평균" 비교
- 기간 스티커 (`packages/core/src/weather.ts` SEASONS, **기본값 — 사장님 확인 필요**): 성수기 = 여름방학 7/20~8/20 · 겨울방학 12/24~2/28 · 가정의 달 5월, 비수기 = 개학 3/2~3/31 · 장마 6/20~7/10 · 11월, 나머지 평상시
- 작년 자료가 기간의 80% 미만이면 비교(%)를 하지 않고 "작년 자료 n일치뿐"으로 표시

## 8. 마감 때 근무자 조작 (목표: 1~2번) → 사무실 방식으로 0번 (2026-10-02)

백오피스가 웹이라 사무실에서 받을 수 있음을 확인 → 아래 표의 매장 방식은 쓰지 않음 (DB 읽기 코드는 남겨 둠).


| 방법                              | 근무자 조작                                                          | 필요한 것                         |
| --------------------------------- | -------------------------------------------------------------------- | --------------------------------- |
| 엑셀 폴더 (지금 만든 것)          | OK포스 백오피스에서 보고서 조회·저장(여러 번) → **매출 보내기**      | 없음                              |
| DB 직접 읽기                      | **매출 보내기** 1번 (카페는 22:10 자동이라 0번)                      | OK포스 읽기 전용 계정             |
| DB 사본 읽기 (계정 없이, 검토 중) | **매출 보내기** 1번                                                  | 사장님 결정 (아래)                |

- 엑셀 방식은 목표(1~2번)에 못 미칩니다. 계정이 오기 전 임시로만 씁니다.
- 계정 없이 1번으로 하려면, POS DB 파일의 **사본**을 만들어 사본만 읽는 방법이 있습니다 (Firebird 내장 엔진은 사본 파일을 비밀번호 없이 열 수 있음).
  원본·OK포스는 건드리지 않지만 OK포스가 걸어 둔 DB 비밀번호를 우회하는 셈이라, OK포스 이용 약관·유지보수에 문제가 없는지 사장님 확인 뒤에 만듭니다.
